# Native 按接收端回报协商缓冲

日期：2026-10-18。用户明确要求实现 Music Assistant 风格的自动协商与按设备适配，不能将2秒变成新的日常固定值，不能反复要求听短音；保留Windows原生控件，断网测试暂缓。

## 参考与边界

Music Assistant airplay-cli HEAD已核对为 `1701bc25e9d303b42532569f624b64c0d0afb1f6`。参考其[流SETUP与边界读取](https://github.com/music-assistant/airplay-cli/blob/1701bc25e9d303b42532569f624b64c0d0afb1f6/src/ap2_client.c)和[调度设计](https://github.com/music-assistant/airplay-cli/blob/1701bc25e9d303b42532569f624b64c0d0afb1f6/DESIGN.md#6-timing-and-the-start-contract)：读取设备回报、钳制参数、单独记录arrival-to-render。它自己的固定2000ms lead与预录媒体预填充不移入当前实时WASAPI采集路径。当前已可听NTP锚点、采样节奏、音量校准和门控不改。

自动协商是请求与回包约束选择，不是自动测得声学延迟或保证最低可听延迟。成功发包、健康feedback、非零PCM都不自动写入听音资格。其他型号/固件/系统的实际资格没有扩大。

## 选择规则

Native的内部IPC使用 `latency_policy="negotiate"`，已有每设备 `VerifiedBufferMs`作为可空偏好。旧面板/显式probe仍为默认fixed模式，显式0与独立min/max行为保留。Native启动要求包内引擎明确声明支持该能力，以避免旧引擎把未知值当作省略参数。

| 设备资料 | 请求与选择 |
| --- | --- |
| 已有听音参考，设备不回报边界 | 保留该设备参考，当前mini仍为100..100ms；来源verified_reference |
| 无参考、无回报 | 使用成熟实时发送器的250..2000ms兼容协商范围，以250ms作为未验证的兼容选择；2000ms仅是请求范围上界，没有两秒等待或预填充 |
| 有合法设备边界 | 以回报为权威；将已有偏好钳入该范围，无偏好时优先选择回报下界；仅上界时限制兼容选择 |
| 边界为0或缺失 | 该边未知，保留原始诊断，不伪造测量 |
| 类型错误、负数、越界或矛盾窗口 | 有本设备已验证参考时回退并记录原因；没有参考则明确失败，不假称协商成功 |
| 合法下界超过产品支持能力 | 明确失败，不把设备最低要求偷偷钳低 |

边界以采样帧解析，最小值向上取整为毫秒、最大值向下取整；取整后无可表示交集也失败。接收器报告的窗口可能覆盖原请求偏好，诊断同时保留原offer与有效选择。`arrivalToRenderLatencyMs`仅作信息，不叠加到时序或作为缓存容量。

只有接收端最大窗口参与自动模式的重传截止；下界不作为实际播放期限。无最大值时使用已有一秒有界历史恢复机会。该窗口不增加正常发送等待；固定旧模式的期限保持。

## Windows集成

取消“缺少听音缓冲记录就不能启用”的新门槛，音量校准、驱动、端点、重启和型号/固件资格仍必须有效。首次参考音量校准确认不再自动把2000ms写为日常缓冲；已有100等人工听音记录保持。

协商前目标值保持未知；仅接受当前session、预期host、匹配偏好与采样率的结构化回报。新连接、重连及设备身份变化会清空旧结果；不会把另一台设备的窗口沿用。协商来源与原始范围进入诊断日志，不增加日常控件，也不自动覆写持久听音参考。
