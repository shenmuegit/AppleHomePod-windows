# AppleHome 0.2.0 Preview 4

Automatic mDNS failover when Windows discovery accepts queries but stops returning devices.

**Overnight idle followed by playback has not been tested on hardware.** This prerelease remains limited to the checked combination of Windows 10 Pro 22H2 (build 19045, x64) and one standalone HomePod mini running software 27.0.

## What changed

Preview 3 could keep reopening an unresponsive Windows DNS-SD provider even while HomePod was reachable. Preview 4 switches to the existing managed mDNS implementation when the silent-query maintenance deadline expires, then rediscovers the qualified device and reconnects.

- No IP address, network-adapter selection or system network change is required. Provider selection is held in memory for the affected discovery interface.
- Explicit permission errors and invalid requests retain their existing handling. Device identity, firmware/group qualification and authentication checks remain enforced.
- The approximately 30-second silent-detection window is retained. It is not a guarantee of audible playback within 30 seconds; discovery, handshake and audio startup also take time.
- Windows volume controls, device binding/calibration, per-device timing records, the audio engine and setup UI are unchanged. Setup continues to follow Windows display language preferences.

## Installation

1. Download `AppleHome-0.2.0-366a8ee1d869.zip`, extract it and open `AppleHome.exe`.
2. Follow the wizard to install the audio driver if needed, connect HomePod and confirm audio. Save your work and restart Windows if the driver requires it.
3. Use your usual players and the Windows output, volume and mute controls.

**Existing users:** reopening the wizard reuses the installed app. Follow `INSTALL.md` or `INSTALL.zh-CN.md` to replace the older background while retaining a qualified device record. There is no automatic updater. A full fresh-driver installation and restart have not been rerun for this release.

## Validation

- **830 .NET regression tests** passed locally. Four new cases cover queries that never return, expiry after an initially successful result, explicit permission errors and invalid requests. The first two failed before the fix; the explicit-error cases remain protected.
- **23 published-app English UI checks** passed with a simulated device and no audio. The setup layout is unchanged.
- The installed final binary was checked in the actual failing environment. Windows DNS-SD returned an empty device list with no errors, while direct mDNS and the existing managed implementation found the same qualified HomePod.
- The background automatically switched providers at 11:17:16 on 2026-10-22, rediscovered the device about 0.35 seconds later and started streaming at 11:17:17. The listener confirmed that normal music had recovered and remained continuous.
- At the recorded observation, 16945 nonzero PCM packets had been sent with zero send or synchronization errors. Internal capture-to-send p95 was about 36 ms; this is **not** measured acoustic latency. Windows output, volume, binding and calibration were preserved.

No generated audio, short tones, PCM recording or microphone capture were used for the hardware checks. No network settings were changed and no disconnection test was performed. These are local checks; the repository has no configured GitHub Actions workflow. A static compatibility audit still has 1555 unconfirmed imports and does not qualify untested Windows environments.

## Compatibility and remaining checks

The native wizard enables the single HomePod mini `AudioAccessory5,1 / 27.0` profile. Other Windows 10 builds, Windows 11, other HomePod models or firmware, stereo pairs and Apple TV groups remain unvalidated and are not newly enabled.

**Actual overnight idle and subsequent playback remain untested.** This recurrence followed a PC boot. The underlying system trigger that makes Windows discovery stop returning results remains unknown; this update provides application recovery from that state. Sleep/wake, physical network-outage recovery and other Home access/PIN policies still need hardware checks. Manual volume/mute cycles, 30-minute playback and sustained video synchronization were not repeated for this binary. The executable is unsigned and has no automatic updater. See the [compatibility record](https://github.com/shenmuegit/AppleHomePod-windows/blob/main/docs/COMPATIBILITY.md).
