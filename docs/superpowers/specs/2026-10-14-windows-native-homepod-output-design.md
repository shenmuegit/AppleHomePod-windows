# Windows 原生 HomePod 输出设备设计规格

日期：2026-10-14。状态：**2026-10-15 用户在计划交接后继续，进入 Native inline 实施；独立驱动尚未安装。**

## 1. 已确认的使用目标

用户要求将日常操作收敛到 Windows 自带的音频输出选择、音量和静音：选择 HomePod 即可播放，切回其他输出即可恢复该输出，无需独立 AppleHome 控制面板。用户已选择独立设备路线，并接受一次驱动安装。首轮仍使用现有 Windows 10 与单只 mini 27.0，断网测试暂缓。

本规格替代原规格中“日常通过 WPF 面板主动开始”和“首版不安装虚拟音频设备”的相关选择。原有认证验证、GPL 来源、数据隔离、边界校验和未实测组合不得冒称支持等要求继续有效。

## 2. 日常交互

1. 首次按第 4 节独立安装驱动，绑定当前 mini；完成后 Windows 输出列表显示 `HomePod – da`。
2. 在任务栏或 Windows 声音设置选择该输出。后台自动发现、认证和发送该虚拟端点的声音。
3. Windows 音量、静音键和混音器控制这路声音。日常不显示 AppleHome 音量、开始、停止、缓冲或均衡器面板。
4. 选择电脑扬声器或耳机时，后台结束不再需要的 HomePod 发送；声音由 Windows 送到用户选择的设备。
5. 正常空闲、暂停或静音保持可恢复状态；再次播放不要求打开应用。
6. 错误使用简短的系统通知与诊断日志；诊断入口只在明确请求排障时使用。

第一轮绑定一只已确认的 mini，稳定身份来自本地发现记录；不按易变化的 IP 地址或设备名称重新猜测接收端。接收端改名不改变绑定身份；诊断显示新名称，Windows 端点名称仅在明确执行绑定维护时更新，不由普通权限后台自动改写，且保留用户自己的端点改名。多台独立 HomePod 的一机一端点管理留待后续规格，不在本轮引入。

## 3. 声音路径与后台职责

```text
Windows 应用及原生混音器
          ↓
独立虚拟播放端点：HomePod – da
          ↓ 明确绑定的虚拟端点音频
当前用户的 AppleHome 后台组件
          ↓ 复用原生 NTP / ALAC 发送
HomePod mini
```

物理扬声器不承担这条输出的采集或中转。新模式不设置物理播放设备静音，不调用旧的本机静音保护来消除双播。迁移前先停止旧流，恢复仍由旧应用拥有的静音状态。

后台优先复用现有 .NET、NAudio、Rust 引擎和 JSONL 接口，日常进程运行在当前用户上下文，不显示窗口或托盘控制菜单。安装绑定完成后建立当前用户登录启动及失败后有界重启的系统计划任务；默认输出为 HomePod 时恢复用户保存的选择，其他输出被选中且虚拟端点无播放需求时不建立 HomePod 音频会话。任务仅启动本应用后台程序，不保存账户密码，不安装系统级常驻音频服务。

监听默认渲染端点及相关音频会话变化，合并重复角色通知。应用明确单独路由到该虚拟端点也构成发送意图；不能只检测全局默认后忽略仍在使用该端点的应用。Windows 原生混音器继续管理应用音量，后台不修改其他应用的音量或输出偏好。

后台在绑定端点完成采集准备后进入就绪状态；此后握手前后的首段音频使用有界暂存。尚未完成采集初始化的后台冷启动空窗须单独测量，不能声称找回此前未采集的声音。更换输出或接收端代际时清除旧暂存，不在恢复后重放历史声音。暂存溢出明确失败，不靠静默丢掉首段声音宣称成功；启动暂存造成的额外延迟独立记录。原有严格认证继续适用，认证失败不得传输。

依据：[Windows 端点机制](https://learn.microsoft.com/en-us/windows/win32/coreaudio/audio-endpoint-devices)、[默认设备通知](https://learn.microsoft.com/en-us/windows/win32/api/mmdeviceapi/nf-mmdeviceapi-immnotificationclient-ondefaultdevicechanged)。

## 5. 原生音量与静音

Windows 原生控件是唯一日常音量入口。设备主音量、设备静音和应用混音器必须分别改变实际声音，不能仅让滑块数值变化。

将设备主音量/静音通知落实到实际输出控制，应用混音器增益由 Windows 保留。来自后台自身的状态同步要带上下文标记，避免回调循环和过时读数覆盖用户的新操作。第一轮不把 Windows 百分比线性换算为 HomePod 百分比；HomePod 当前非零音量作为实体扬声器的参考级别，不在连接时自动拉到 100%。

在最终确定增益应用点之前，先用低峰值已知信号校准该驱动的 PCM 取样位置：主音量是否已经进入所取 PCM、静音如何呈现、不同 dB 档位对应的样本与实际声音。每个增益只应用一次，不能同时叠加 Windows 主音量、旧应用增益和重复的 HomePod 音量映射。

若所取样本已经包含设备主音量，则非静音时发送增益为 1；若没有包含，则发送增益采用 `10^((当前 dB - 端点最大 dB)/20)` 并限制在 0–1。Windows 标量为 0 或静音时发送增益为 0；不叠加旧应用主音量或均衡器。具体链路由校准结果固定，不能要求用户自行配置。

首次连接遵循实际接收端音量与用户最新操作，避免初始化造成突增。接收端实际音量为 0 且没有更新的 Windows 正向播放意图时，保持接收端为 0，并以本应用上下文同步虚拟端点静音；用户随后通过 Windows 取消静音时，只恢复到实测校准保存的非零参考音量，并等待协议回读。没有可验证的参考音量时停止初始化，不猜测恢复值。连接准备期间先确定增益和接收端状态，再释放暂存；明确静音或更新音量不能导致旧的较大声音在随后被重放。0、静音与恢复都必须听音验证。

若所选驱动不能提供满足上述规则的稳定取样与控制路径，停止将其作为交付基线，带实测证据复核驱动选择；不能以无效的 Windows 滑块宣称完成。

依据：[EndpointVolume API](https://learn.microsoft.com/en-us/windows/win32/coreaudio/endpointvolume-api)、[设备和会话音量](https://learn.microsoft.com/en-us/windows/win32/coreaudio/volume-controls)。

## 6. 暂停、故障与路由

正常静音和暂停不使用“有声样本未推进”推断物理播放设备需要恢复，因为新模式不存在被应用静音的物理端点。音频恢复后继续既有会话，或在明确的会话结束后重新连接；两者都不要求控制面板操作。

输出变化、端点删除、后台退出和引擎失败必须取消对应会话并释放资源。接收端暂不可用时给出系统通知，重试保持有界。后台不得擅自把用户选择的声音改送到物理扬声器。

切回其他输出时停止提交新的 HomePod 样本，并清除不再适用的暂存。HomePod 已缓冲的尾音与切换体验独立记录，不能把停止发包直接当作扬声器已经静音。

只读取明确绑定的虚拟播放端点。不开放物理麦克风，不录制用户音乐，不改变防火墙、驱动签名策略或现有 Voicemeeter 配置。

## 7. 协议与兼容边界

当前 mini 继续使用已实测的 NTP / ALAC / 44100 Hz 与 2000 ms 目标配置。正常界面不暴露缓冲、时钟、编码或采集源设置。

虚拟输出解决本机与 HomePod 共用物理播放路径的问题；网络缓冲仍存在。声学延迟和视频同步继续按测量结果判断，不能承诺零延迟。Windows 11、其他 HomePod 型号/固件及立体声对继续保留待验收状态。

## 8. 验收条件

| 项目 | 必须取得的实际证据 |
|---|---|
| 安装与身份 | 官方包与签名核对；独立端点出现；其他设备、Voicemeeter 路由和默认输出保持用户选择 |
| 原生选择 | 只用 Windows 输出选择完成开始和切回；正常使用不弹出控制面板 |
| 声音隔离 | HomePod 接收到已选择的声音；物理扬声器无该声音的先行副本 |
| 首段和切换 | 短促声音不被握手吞掉；更换输出不重放旧暂存；记录尾音 |
| 音量与静音 | 校准增益位置；Windows 主音量和应用混音器有效；0/静音无声、恢复可听；无重复衰减或初始化突增 |
| 暂停恢复 | 音乐暂停/静音至少 15 秒，恢复后 HomePod 正常播放，路由不改送本机 |
| 持续播放 | 完成一次实际 30 分钟播放与用户听音确认，记录真实观察窗口、资源、重启/错误和可见异常 |
| 退出与恢复 | 后台/发送进程结束后资源被释放，其他输出可正常使用；不依赖全局静音恢复 |
| 回归 | 原有认证、IPC 边界、取消、设置隔离回归通过；增加输出选择代际、音量回调及静音恢复测试 |

真实断网测试依用户要求继续暂缓。无对应设备的兼容项继续明确列出，不能用软件模拟代替硬件验收。

## 9. 实施与审阅边界

先审阅本规格，再形成带驱动安装范围、权限和校准门槛的实施计划。后续实现复用已有组件，只增加系统端点绑定、后台输出状态与原生音量连接所需部分。

当前可用的旧便携包保留作基线。新模式通过上述原生选择、声音隔离和原生音量验收后，才替换日常入口；测试记录分别注明版本与声音路径。
