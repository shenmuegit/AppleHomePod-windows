# Windows HomePod 音频发送应用设计规格

日期：2026-10-14（北京时间）。状态：用户已明确回复“规格通过”；进入实施计划审阅阶段。产品暂用工作名 AppleHome。

## 1. 用户目标与成功标准

用户希望在 Windows 10/11 上将系统声音、音乐和视频播放器声音发送到 HomePod；HomePod mini、第 1 代和第 2 代都纳入支持目标，目前可用验收设备是 HomePod mini。用户接受 GPL 开源，并已确认复用 AirFlash 的原生 Windows 结构，先跑通 mini，再逐项验证其他型号及已有立体声对，视频同步按实测判断。

成功意味着用户能在桌面应用中找到并选择 HomePod，主动开始发送所选 Windows 播放端点的声音，调节音量、停止发送，并在错误、断线和退出后得到正确的声音状态与明确提示。只有记录了型号、固件、Windows 构建号和实际出声证据的组合才标记为“已验证”。模拟器或发包日志成功只能证明对应软件环节。

首轮局域网基线为 IPv4、PC 与 HomePod 可相互通信、允许本应用所需 mDNS 和协商后的本地音频/时钟通信。IPv6、Windows ARM64、跨 VLAN 及多个独立房间的同步播放不在未验收时列为支持。

## 3. 复用策略与来源

优先验证的基础是 [AirFlash](https://github.com/Ding-Kyoma/AirFlash)，调研锚点提交 `cf420d97700463c56adc31408510e8336e99e51c`。正式开发必须固定实际使用的上游提交，保留来源、版权、GPLv3+ 许可证和第三方依赖说明，不依赖浮动 `main` 构建。用户已接受 GPL 路线；没有签订商业许可证时不采用其商业许可条款。[上游许可证](https://github.com/Ding-Kyoma/AirFlash/blob/cf420d97700463c56adc31408510e8336e99e51c/LICENSE)

复用现有 WPF/.NET 界面、Windows 设备发现、Rust 引擎、调用边界与有意义的测试，不从零重写 AirPlay，不新增第二套音频引擎。先证明基础在本机和 mini 上工作，再按实测失败点做最小修复。上游 Windows 10 修复仍是兼容候选，不能预先认定可用。[上游兼容说明](https://github.com/Ding-Kyoma/AirFlash/blob/cf420d97700463c56adc31408510e8336e99e51c/docs/WINDOWS-COMPATIBILITY.md)

若固定基础无法构建或无法出声，先保存可复现的失败证据，判断修复成本；只有基础路线需要实质变化时才回到设计讨论。不能用仅有 UI 的演示替代音频闭环。

## 4. 组件与数据流

```text
Windows 应用 → 指定播放端点 → WASAPI loopback → 重采样/有界缓冲
                                                   ↓
WPF 托盘与控制面板 ← JSONL v1 → Rust 会话、认证、时钟、音频传输
        ↓ Windows DNS-SD                             ↓
   局域网接收端列表                           局域网 AirPlay → HomePod
```

WPF 负责交互、发现、设置、会话状态和本机音频状态恢复；Rust 负责采集、样本转换、配对验证、加密控制和音频、时钟同步、反馈重传及资源清理。界面与引擎沿用已有标准输入/输出 JSONL v1 接口，带请求和会话标识；不另外建立 HTTP 服务或云端音频转发。[现有进程接口](https://github.com/Ding-Kyoma/AirFlash/blob/cf420d97700463c56adc31408510e8336e99e51c/desktop/AirFlash.Core/EngineConnection.cs)、[引擎说明](https://github.com/Ding-Kyoma/AirFlash/blob/cf420d97700463c56adc31408510e8336e99e51c/native/airflash-engine/README.md)

共享模式 WASAPI loopback 采集所选端点的混合音频，默认使用当前系统输出，同时允许选择其他现有端点。应用输出到别的端点时必须提示选对采集源。独占模式和受保护内容的限制要在说明中列出，不能为捕获它们修改系统保护。[Microsoft：Loopback Recording](https://learn.microsoft.com/en-us/windows/win32/coreaudio/loopback-recording)

## 5. 用户流程

1. 启动后处于停止状态，显示设备列表、采集源、音量和当前状态。没有用户的开始操作，不启动声音采集。
2. 用户选择 HomePod 与采集源，点击开始。界面逐步显示连接、认证、协商和发送状态，连接过程可以取消。
3. 若设备要求配对或不允许访问，显示对应说明。完成有效认证后才进入音频发送。
4. 用户可调节音量、选择是否保留本机播放、停止或切换设备。切换前必须清理旧会话。
5. 关闭主窗口时保留已有托盘行为并明确提示；托盘退出必须停止采集、结束引擎和恢复由应用改变的声音状态。

基础控制保持紧凑，沿用已有可访问组件，支持键盘操作、可读焦点和状态文字；错误和状态不只靠颜色表达。没有必要新增家庭设备控制、账号、云同步、EQ、自研驱动或开机自动发送。

## 6. 发现与连接规则

发现读取 `_airplay._tcp` 与 `_raop._tcp` 等基础项目已有服务，按设备身份合并，避免同一台 HomePod 显示两次。使用用户选定的可用网卡，允许重新扫描和受验证的手动 IPv4/端口输入；不能把手动 IP 可连接视为自动发现已通过。

设备能力综合广播信息与 `/info` 响应，保留型号和协议版本用于诊断。不能只对白名单中的 mini 型号开放发送。时钟路径和 PCM/ALAC 的使用遵循引擎协商与实际测试结果，不能把另一项目对某型号的假设硬编码为通用事实。

IP、端口、报文长度、IPC 版本、会话标识、音量范围和设备响应均需在边界验证；保留基础项目的超时、取消和报文大小限制。认证证明或接收端身份验证失败必须终止，不切换为允许失败的模式。

## 7. 访问模式与配对资料

HomePod 初始设置仍由 Apple 支持的 iPhone/iPad 流程完成。应用不承担 Apple 家庭初始化或 Apple Account 登录。[Apple 设置指南](https://support.apple.com/en-us/111110)

首轮实机基线为家庭 App 允许同网访问的 HomePod。必须分别记录以下结果，不能将其中一种成功宣传为所有访问方式均支持：

- 同网允许访问：验证现有瞬时认证通路。
- 持久 PIN 配对：保留基础实现，只有当前设备可完成有效配对才标记通过。
- 家庭 App“要求密码”：当前引擎直播参数没有任意扬声器密码入口，需单列为未验证/待适配，失败时明确提示访问设置。不得把数字配对 PIN 与任意扬声器密码混为一谈。
- 仅家庭成员可访问：无法满足授权时停止并解释原因，不能绕过家庭访问限制。

Apple 官方区分上述访问范围和“要求密码”开关；应用不自动修改这些设置，也不要求用户开放给所有附近的人。[Apple：允许他人播放与密码设置](https://support.apple.com/en-gb/guide/homepod/apdb68d3dec5/homepod)

需要保存的配对资料使用当前 Windows 用户绑定的 DPAPI，沿用基础实现的身份验证，不明文写入设置、日志或诊断导出。AppleHome 使用自己的应用数据目录，不读取、覆盖或迁移既有 AirFlash 等产品的设置或凭据。

## 8. 本机声音状态与会话生命周期

“只通过 HomePod 播放”不能简单通过把 Windows 音量设为零来实现，因为部分设备会使 loopback 也无声。沿用基础项目已有静音和恢复机制，并通过真实采集验证；若当前驱动无法隔离本机出声，恢复原状态、提示原因，并提供保留本机播放或选择其他现有端点的路径。

应用改变静音、音量或端点之前记录原状态。停止、连接失败、网络丢失、采集端点移除和退出均需释放本次拥有的资源并恢复状态；恢复前检查当前状态，避免覆盖用户在发送期间主动做出的新选择。崩溃恢复只能处理本应用记录的状态，不重置整个 Windows 声音设置。

状态至少区分：已停止、连接中、正在发送、重连中、错误。正在发送意味着引擎处于有效会话并持续处理音频，不等于已经声学确认 HomePod 出声；静音输入需能和断流故障区分。重连仅针对用户已开始的会话，沿用基础项目的有界重试，用户停止后不得重新采集或自动重连。

## 9. 音乐、视频和延迟

音乐目标是稳定音频与正确恢复。视频音频也走同一声音通路，但实际画声同步单独验收。使用现有稳定和较低缓冲设置，界面只能把它们称为目标或档位，不能把目标值显示为实测声学延迟。

独立发送器无法统一控制所有浏览器和播放器的视频时间线。因此第一版提供实际偏移的测试方法和支持同步调整播放器的补偿说明，记录未补偿与补偿后的结果。不承诺所有网页视频自动嘴型同步，不宣传零延迟，也不将游戏/会议低延迟作为默认能力。上游也明确没有跨型号 200ms 保证。[引擎限制](https://github.com/Ding-Kyoma/AirFlash/blob/cf420d97700463c56adc31408510e8336e99e51c/native/airflash-engine/README.md)

## 10. 错误、隐私与网络

错误至少能区分：未发现设备、网络不可达、访问/认证失败、配对待输入、采集源不可用、引擎启动失败、协议协商失败和发送中断。错误文本给出下一步操作，不暴露报文中的密钥或凭据。

音频只在内存处理并发送到用户选择的局域网接收端，默认不录音落盘，不采集麦克风，不增加遥测。诊断只保存必要状态和性能信息；导出内容排除凭据与音频，并脱敏用户路径及设备标识。

防火墙诊断说明本应用为何需要局域网发现及协商后的入站时钟/控制通信；规则限定本应用和所需网络范围，提供移除方式。不关闭防火墙，不复制上游示例中对所有网络配置文件开放的宽泛规则，不更改系统执行策略。

## 11. 验证要求

| 层级 | 必须验证的内容 | 能证明什么 |
| --- | --- | --- |
| 构建与启动 | 固定来源可重复构建，正常启动，托盘可退出，引擎 hello 可读 | 二进制与进程边界可工作 |
| 自动化逻辑 | 设备去重、输入拒绝、认证失败关闭、会话标识、停止/取消、重试取消、状态恢复 | 对应分支有可重复回归证据 |
| 传输与音频 | 复用独立 SRP/加密向量、模拟接收端、ALAC 解码、RTP 序号及时间戳、有界缓冲和静音持续输入测试 | 协议与音频处理符合对应测试 |
| mini 实机 | 型号/固件/Windows 版本、发现、短时低音量出声、音量、停止、本机状态恢复 | 该明确组合完成真实闭环 |
| 稳定性 | 用户实际播放音乐，记录持续时长、静音后恢复、断网/端点变化、错误与恢复 | 已观察时段的稳定性，不能写无限稳定 |
| 视频 | 点击/画面标记与声音对照，记录测量方法、偏移和播放过程漂移 | 当前环境的画声偏移，不是缓冲参数 |
| 其他平台/型号 | Windows 11、第 1/2 代、双机对逐项重复必要流程 | 仅各自测试过的组合 |

复用上游已有有意义的测试。新增非平凡修复必须有能复现问题的最小回归测试；不为文案和外观变化添加镜像实现的测试。自动实机探测沿用基础项目短时低音量程序，长时间真实播放与纯软件 soak 的证据分开。[上游实机与兼容验收说明](https://github.com/Ding-Kyoma/AirFlash/blob/cf420d97700463c56adc31408510e8336e99e51c/docs/WINDOWS-COMPATIBILITY.md)

首次进入“可用测试版”的最低条件为：本机 Windows 10 与用户 mini 完成上述真实闭环；Windows 11 与其他型号若没有对应执行条件，必须在发行说明中列为待验证。最终全型号支持目标仍保留，不能因首轮完成而将整个项目目标标为完成。

## 12. 交付与实施边界

首轮交付可本地启动的原生应用、使用说明、固定上游来源与许可证、测试结果及兼容矩阵。优先便携 x64 包，沿用基础项目打包路径；是否补充安装包取决于现有打包成本，不另建更新服务。

正式实施前先检查本地已有 Rust、.NET 与 C++ 工具路径。当前只读检查已发现本机 Windows 10 build 19045、Python 3.11.9；默认 PATH 未发现 cargo，dotnet 未列出 SDK，C++ 工具组件已存在。实际是否需要安装，以实施前检查为准，不静默切换全局默认运行时。

本规格不授权发布外部仓库、发送消息、购买产品或证书，也不包含家庭设备控制。下一步按 Superpowers 流程审阅本规格，通过后再形成书面实施计划并确定执行方式，随后开始实现。
